# ЛР №6 — Взаимодействие компонентов по модели Pub/Sub (Интернет-магазин)

Продолжение ЛР №5 (`lab-005`). Вариант предметной области — интернет-магазин (ЛР №1).
Событийная модель реализована средствами C# (без Kafka/RabbitMQ/ActiveMQ).

## Архитектура

```
Client ──TCP/JSON──► Server ──► PubSubRequestProcessor ──► BusinessLogic (ЛР №5: Primary/Replica)
                                        │
                                        └─ после OrderCreated / OrderCancelled / PaymentCompleted
                                              ▼
                                         Publisher ──► Broker-1 / Broker-2 (failover) ──► очередь ──► Logger
                                                              ├──► очередь ──► StockService
                                                              ├──► очередь ──► NotificationService
                                                              └──► очередь ──► AnalyticsService (подключается во время работы)
```

| Компонент          | Файл                                    | Назначение                                                                                                                                                                                                                         |
| --------------------------- | ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DomainEvent`             | `Shared/Events.cs`                        | Событие: `EventType`, `EntityId`, `ClientId`, `Timestamp`, `Data`                                                                                                                                                           |
| `Publisher`               | `Server/PubSub/Publisher.cs`              | Передает событие Broker, возвращает `PublishResult`, фиксирует ошибку публикации                                                                                                         |
| `Broker`                  | `Server/PubSub/Broker.cs`                 | Принимает события, хранит подписки, ставит событие в очередь каждого подписчика, повторные попытки (3), dead letter, повторная доставка |
| `Subscriber` + 4 типа | `Server/PubSub/Subscribers.cs`            | Logger (1 с), StockService (3 с), NotificationService (2 с), AnalyticsService (0.5 с); имитация отказа через `Available`                                                                                            |
| `PubSubSystem`            | `Server/PubSub/PubSubSystem.cs`           | Сборка Broker/Publisher, регистрация подписчика по имени                                                                                                                                                   |
| `PubSubRequestProcessor`  | `Server/PubSub/PubSubRequestProcessor.cs` | Декоратор над `BusinessLogic`: публикует события без изменения бизнес-логики и Publisher                                                                                              |
| `PubSubScenarios`         | `Client/PubSubScenarios.cs`               | Эксперимент «отказ подписчика, новый подписчик, повторная доставка»                                                                                                               |
| `PubSubTests`             | `Tests/PubSubTests.cs`                    | 12 unit-тестов (без PostgreSQL)                                                                                                                                                                                                     |

### Подписки

| Subscriber                    | Подписка                               | Задержка |
| ----------------------------- | ---------------------------------------------- | ---------------- |
| Logger                        | OrderCreated, OrderCancelled, PaymentCompleted | 1 с             |
| StockService                  | OrderCreated                                   | 3 с             |
| NotificationService           | OrderCreated, PaymentCompleted                 | 2 с             |
| AnalyticsService (новый) | все три типа                         | 0.5 с           |

Каждый подписчик обрабатывает события в собственной очереди и своей задержкой, поэтому обработка независима.

### Отказ и восстановление

- Отказ подписчика (`SetSubscriberAvailable`) — каждая попытка завершается `SubscriberUnavailableException`.
- Broker делает до 3 попыток с паузой 300 мс; после неудачи событие уходит в dead letter.
- Broker не аварийно завершается: остальные подписчики продолжают получать события.
- `RedeliverDeadLetters` ставит недоставленные события в очередь повторно (после восстановления подписчика).
- Отказ Broker (`SetBrokerAvailable`): Publisher возвращает `Success = false` с текстом «Broker недоступен», бизнес-операция уже выполнена, сервер продолжает работу.

### Журнал

Серверный лог содержит строки вида `Client N → Publisher → PUBLISH`, `Client N → Broker → EVENT RECEIVED`,
`Broker → StockService | QUEUED`, `StockService → SUCCESS`, `StockService → Attempt 1 → FAIL | ...`,
`Broker → StockService → DEAD LETTER`.

## Запуск

Требования: .NET SDK 10, PostgreSQL (`docker compose up -d`, как в ЛР №5).

```bash
dotnet run --project Server    # терминал 1: сервер, два Broker и подписчики
dotnet run --project Client    # терминал 2: интерактивное меню, все сценарии запускаются из него
dotnet test --filter FullyQualifiedName~PubSubTests   # unit-тесты (БД не нужна)
```

Пункты меню клиента: 16 — состояние Broker и подписчиков, 17 — отказ подписчика, 18 — отказ Broker, 19 — подключить AnalyticsService,
20 — повторная доставка dead letter, 21 — основной сценарий, 22 — повторные попытки, 23 — два Broker, 24 — несколько клиентов, 25 — задержки.
(Те же сценарии доступны без меню: `dotnet run --project Client -- pubsub [retry|failover|clients|timings]`.)

Каждый сценарий сначала сбрасывает данные (`Reset`), поэтому остатки товаров не зависят от предыдущих запусков.

## Результаты (живые запуски на PostgreSQL)

### Анализ задержек (пункт 25, одно событие OrderCreated)

| Подписчик  | Очередь, мс | Обработка, мс | Всего, мс | Попыток |
| ------------------- | -------------------- | ------------------------ | ---------------- | -------------- |
| Logger              | 0                    | 1000                     | 1000             | 1              |
| NotificationService | 0                    | 2001                     | 2001             | 1              |
| StockService        | 0                    | 3001                     | 3001             | 1              |

- Время операции клиента (бизнес-логика + публикация): **517 мс**, подписчиков оно не ждет.
- Завершение всех подписчиков: **3001 мс** (самый медленный). Сумма времен обработки 6002 мс — подписчики работают параллельно, а не друг за другом.
- Очередь подписчика последовательная: при трех заказах подряд StockService обработал их за ~9 с, на каждого уходит 3 с.

### Повторная доставка (пункт 22)

NotificationService: два временных сбоя → `Attempt 1 → FAIL`, `Attempt 2 → FAIL`, третья попытка `SUCCESS`, общее время 2610 мс (2 паузы по 300 мс + 2 с обработки). Dead letter пуст.
Если сбоев больше числа попыток (3), событие уходит в dead letter и может быть доставлено повторно после восстановления.

### Два Broker (пункт 23)

| Шаг | Состояние                | Результат публикации                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------ | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1      | Оба доступны           | через Broker-1                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |

| 3      | Оба отказали           | `не опубликовано: Broker недоступен (проверено Broker: 2)`, заказ при этом создан, сервер работает                                                                                                                                                                                                                                                                                                                                                                                        |
| 4      | Оба восстановлены | снова через Broker-1                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |

Анализ: несколько Broker нужны для отказоустойчивости самого посредника и распределения нагрузки.
При отказе одного Publisher переключается на другой. Новые проблемы: события в очереди отказавшего Broker остаются в нем
(здесь — в памяти, при перезапуске теряются); возможны дубликаты и нарушение порядка событий между Broker; нужна общая
конфигурация подписок (здесь подписчик регистрируется сразу в обоих Broker); у каждого Broker свои счетчики и dead letter.

### Несколько клиентов (пункт 24)

Три клиента одновременно создали заказы 1, 2, 3 → доставлено 9 из 9 событий OrderCreated (по 3 каждому подписчику), ошибок нет.

### Сравнение прямого взаимодействия и Pub/Sub

| Критерий                             | Прямое взаимодействие                                                 | Pub/Sub                                                                                                                                                          |
| -------------------------------------------- | ----------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Кто о ком знает                  | Сервер знает каждый компонент                                   | Publisher знает только Broker; подписчики — только Broker                                                                            |
| Где маршрутизация            | В коде сервера (вызовы по очереди)                             | В Broker: по подпискам на тип события                                                                                                    |
| Добавить компонент          | Менять и пересобирать сервер                                     | Зарегистрировать Subscriber (AnalyticsService) — Publisher не меняется                                                                |
| Отказ одного компонента | Ошибка в цепочке вызовов, может сорвать операцию | Остальные получают событие, отказавший — повторы и dead letter                                                        |
| Связанность                       | Сильная                                                                            | Слабая                                                                                                                                                     |
| Цена                                     | Простота, синхронный результат                                 | Асинхронность: результат обработки приходит позже, нужна очередь, повторы и мониторинг |

### Unit-тесты

`dotnet test --filter FullyQualifiedName~PubSubTests` — **22 пройдено, 0 не пройдено**.
Покрыто: создание события; регистрация (включая дубликат и неизвестное имя, регистрация в обоих Broker); доставка подписанному и отсутствие доставки неподписанному;
одно событие нескольким подписчикам; несколько типов; неизвестный тип (0 получателей); некорректное событие; отказ одного и нескольких подписчиков;
продолжение работы Broker; временный сбой с успехом на 3-й попытке и сбой длиннее числа попыток (dead letter); повторная доставка; failover на Broker-2 и возврат на Broker-1;
отказ обоих Broker; добавление нового подписчика без изменения Publisher; замеры времени.

## Ограничения

- Subscriber работают в процессе сервера, а не как отдельные процессы с сетевым подключением к Broker.
- Очереди и dead letter хранятся в памяти и теряются при перезапуске сервера; очереди неограниченные (нет backpressure).
- Дубликаты и порядок между двумя Broker не контролируются.
- Задержки (1/3/2 с) искусственные, заданы в коде подписчиков.
