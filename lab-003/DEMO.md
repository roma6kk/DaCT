## 1. Часть 1 — Race Condition в CreateOrder

### Шаг 1.1. Показать проблему в коде (2 минуты)

dotnet run --project Server/OnlineStore.Server.csproj

dotnet run --project Client

Открыть `Server/BusinessLogic.cs` и прокомментировать XML-документацию класса:

- **Чтение общего ресурса** — `product.Stock`;
- **Проверка** — `if (product.Stock < quantity)`;
- **Изменение состояния** — `product.Stock -= quantity`.

Ключевой тезис: в версии без синхронизации между «проверкой» и «списанием» стоял
`await Task.Delay(10 с)`. Пока первый клиент «обрабатывается», второй проходит ту же
проверку по **еще не измененному** `Stock` → оба списывают последний экземпляр,
остаток становится −1. Это и есть Race Condition: результат зависит от порядка
выполнения потоков.

## 2. Часть 2 — Синхронизация времени с учетом RTT

### Шаг 2.1. Клиент с «спешащими» часами

Перезапустить lock-сервер (состояние уже не важно). Запустить клиент с батарейкой,
спешащей на 7 секунд:

```bash
dotnet run --project Client -- --offset 7
```

В меню выбрать `5` — Синхронизировать время. Ожидаемый вывод:

```
Локальное время клиента:         22:38:50.190   ← часы клиента спешат
Время сервера (ServerTime):      22:38:42.979   ← истинное время
RTT:                             206,3 мс       ← ≥ 200 мс: серверная задержка (Требование 8)
Оценка сетевой задержки (RTT/2): 103,2 мс
Поправка (Offset):               -7102,1 мс     ← ≈ −7000 мс смещения + сетевые/серверные затраты
Скорректированное время:         22:38:43.090   ← теперь совпадает с сервером
```

Что проговорить, показывая `Client/Client.cs` → `SyncTimeAsync`:

```
RTT   = время_получения_ответа − время_отправки   (все по часам клиента)
Delay ≈ RTT / 2    (сервер ответил примерно в середине интервала)
Offset = ServerTime + RTT/2 − ClientTime          (по СМЕЩЕННЫМ часам клиента)
Corrected = LocalTime + Offset
```

Проверка на глаз: `ClientLocalTime − ServerTime ≈ 7,2 с`; `Offset ≈ −7,1 с`;
после прибавления Offset скорректированное время совпадает с временем сервера
с точностью до половины RTT.

### Шаг 2.2. Клиент с «отстающими» часами

Перезапустить клиент с `--offset -5`, снова пункт `5`:

```
Локальное время клиента:         22:39:11.211   ← часы отстают на 5 с
Время сервера (ServerTime):      22:39:16.203
RTT:                             5,0 мс
Оценка сетевой задержки (RTT/2): 2,5 мс
Поправка (Offset):               +4998,5 мс     ← ≈ +5000 мс
Скорректированное время:         22:39:16.211   ← совпало с сервером
```

Оба знака смещения скомпенсированы — алгоритм симметричен.

> **Важно не запутаться на защите:** искусственная задержка ответа на TIME_REQUEST
> (200 мс, Требование 8) реализована на **lock-сервере** (`Server/Program.cs`).
> На `Server.SemaphoreSlim` такой задержки нет, поэтому RTT там — единицы миллисекунд.
> Если демонстрируете Часть 2 на SemaphoreSlim-сервере и видите маленький RTT — это
> ожидаемо, Offset корректен в обоих случаях (считается независимо от RTT).

## 5. Шпаргалка ответов на вопросы

- [ ] **Почему 10-секундная задержка вне lock?** Она не работает с общим состоянием; если
  держать ее внутри, клиенты обрабатывались бы строго последовательно (20 с на двоих),
  что противоречит требованию параллельной обработки.
- [ ] **Почему клиенты все равно параллельны?** Критическая секция занимает микросекунды;
  10 с каждый клиент ждет вне ее.
- [ ] **Зачем SemaphoreSlim, если есть lock?** `lock` (Monitor) блокирует поток; при
  большом числе ожидающих задач это расходует потоки пула. `SemaphoreSlim.WaitAsync()`
  паркует задачу без блокировки потока, плюс `Release` в `finally` гарантирует освобождение.
- [ ] **Почему Offset вычисляется через RTT/2?** Не зная одностороннюю задержку, предполагаем
  симметрию сети: запрос шел RTT/2, ответ — RTT/2, значит ServerTime соответствовал моменту
  `ClientTime + RTT/2`. Отсюда `Offset = ServerTime + RTT/2 − ClientTime`.
- [ ] **Почему время измеряется «смещенными» часами клиента?** Иначе смещение не попадет
  в измерения (RTT и интервал считаются по одним часам) и Offset не отразит реальную
  рассинхронизацию — клиент должен жить по своим (неверным) часам, а не по UTC.
- [ ] **Почему после синхронизации время совпадает не идеально?** Точность метода ограничена
  допущением симметрии сети: если путь туда/обратно несимметричен, остаточная ошибка
  ≈ |задержка_туда − RTT/2|.
