# ЛР №5 — Репликация данных и отказоустойчивость (Интернет-магазин)

Продолжение ЛР №4 (`lab-004`). Вариант предметной области — интернет-магазин (ЛР №1), реплицируемый ресурс — остаток товара `products.stock`.

Учебная модель: **Primary → Replica → Failover → Recovery**. Кластер СУБД не создаётся.

## Архитектура

```
Client ──TCP/JSON──► Server ──► InstanceManager ──► Primary (PostgreSQL, порт 5434)
                        │                 │
                        │                 └──────► Replica (PostgreSQL, порт 5435)
                        └──► Replicator: Primary → Replica после каждой операции на Primary
```

| Компонент       | Файл                           | Назначение                                                                                                                      |
| ------------------------ | ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `DbInstance`           | `Server/Instances.cs`            | Экземпляр хранения: имя, строка подключения, флаг имитации отказа                  |
| `InstanceManager`      | `Server/Instances.cs`            | Проверка состояния (AVAILABLE/UNAVAILABLE), выбор экземпляра (failover), признак `ReplicaInSync` |
| `Replicator`           | `Server/Replication.cs`          | Репликация Primary → Replica, сравнение копий, восстановление и синхронизация        |
| `BusinessLogic`        | `Server/BusinessLogic.cs`        | Операции предметной области; запись на Primary сопровождается репликацией       |
| `Db`                   | `Server/Database.cs`             | Строки подключения (Primary/Replica), DDL, сброс данных                                                       |
| `ReplicationScenarios` | `Client/ReplicationScenarios.cs` | Эксперименты: таблица репликации, отказ/Failover/Recovery                                               |
| `ReplicationTests`     | `Tests/ReplicationTests.cs`      | Unit-тесты механизмов ЛР №5 (14 тестов)                                                                           |

Реплицируемые таблицы: `products`, `orders`, `order_items`, `payments`. Таблица `customers` не меняется и одинакова на обоих экземплярах (засеяна при инициализации).

### Состояние экземпляров

- `AVAILABLE` / `UNAVAILABLE` определяется запросом `SELECT 1` с таймаутом 2 с перед каждой операцией.
- Имитация отказа: операция `SimulateFailure` (программное отключение экземпляра). Реальный отказ тоже обрабатывается: остановка контейнера даёт `UNAVAILABLE` через ошибку подключения.

### Репликация (Часть 2)

- Запись всегда выполняется на Primary, затем `Replicator` передаёт изменения в Replica в одной транзакции (заменой содержимого реплицируемых таблиц).
- Передача сериализована семафором, поэтому Replica не получает устаревшие состояния в обратном порядке.
- Если Replica недоступна, сервер фиксирует `Replication → FAIL`, помечает `ReplicaInSync = false` и продолжает работу. Следующая успешная репликация или синхронизация восстанавливает копию.

### Отказ, Failover и Recovery (Части 3–4)

1. Каждый запрос: `Primary → CHECK`. При `UNAVAILABLE` — `Failover → START`, `Replica → CHECK`, `Request redirected to Replica`.
2. Если недоступны оба экземпляра — клиент получает сообщение «Оба экземпляра недоступны: Primary и Replica. Повторите запрос позже». Сервер не падает.
3. Во время отказа записи идут в Replica и **не** передаются в Primary (он недоступен).
4. `RecoverPrimary`: снимает имитацию отказа, проверяет доступность обоих экземпляров, сравнивает копии (расхождения до синхронизации), переносит состояние Replica в Primary (Replica актуальна, так как принимала записи во время отказа), повторно сравнивает копии.

Реплицируется полное состояние таблиц, поэтому частичные изменения от операций без транзакции (`failAt`) тоже попадают в Replica и не нарушают согласованность.

## Запуск

Требования: Docker с Docker Compose, .NET SDK 10.

**Шаг 1. Запуск двух экземпляров PostgreSQL** (Primary — порт 5434, Replica — порт 5435):

```bash
docker compose up -d
```

**Шаг 2. Запуск сервера** (создаёт схемы на обоих экземплярах):

```bash
dotnet run --project Server
```

**Шаг 3. Начальное состояние.** Операция `Reset` (пункт 7 клиента) сбрасывает данные на обоих экземплярах, после чего Primary = Replica. Проверка: пункт 11 (сравнение).

**Шаг 4. Эксперименты:**

```bash
dotnet run --project Client -- scenario replication   # Часть 2: три изменения, таблица репликации
dotnet run --project Client -- scenario failover      # Части 3–4: отказ, Failover, Recovery
```

То же самое интерактивно: пункты 10–15 клиента (состояние экземпляров, сравнение, имитация отказа, восстановление, эксперименты).

**Шаг 5. Тесты:**

```bash
dotnet test
```

Тесты используют базы `onlinestore_test` на обоих экземплярах (порты 5434 и 5435).

### Восстановление и синхронизация (Часть 4)

Расхождения до синхронизации (Replica — актуальная копия):

- `products[3]`: Primary stock = 12, Replica stock = 11;
- `orders[1]`: есть в Replica (status=Created, total=7000), отсутствует в Primary;
- `order_items[1]`: есть в Replica (order=1, product=3, qty=1), отсутствует в Primary.

Расхождений после синхронизации: 0. Контрольная операция `CreateOrder` выполнилась на Primary, после неё `Primary = Replica`.

### Журнал переключения (фрагмент серверного лога)

```
[..] Client 25 → Primary → CHECK
[..] Client 25 → Primary → UNAVAILABLE | имитация отказа
[..] Client 25 → Failover → START
[..] Client 25 → Replica → CHECK
[..] Client 25 → Replica → AVAILABLE
[..] Client 25 → Request redirected to Replica
```

## Обработка ошибок (Требование 5)

| Ситуация                                                                  | Поведение                                                                                                                   |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Primary недоступен, Replica доступна                            | Failover, запрос выполняется через Replica                                                                     |
| Оба экземпляра недоступны                                  | Клиент получает «Оба экземпляра недоступны…», сервер продолжает работу |
| Replica недоступна при репликации                          | `Replication → FAIL`, `ReplicaInSync = false`, операция на Primary сохраняется                             |
| Ошибка синхронизации при восстановлении       | «Ошибка синхронизации: …», Primary не считается восстановленным                      |
| Primary всё ещё недоступен при восстановлении    | «Primary всё ещё недоступен, восстановление не выполнено»                                 |
| Некорректный запрос / неизвестный экземпляр | Ответ `Success = false` с понятным сообщением                                                              |

## Ограничения учебной модели

- Репликация синхронная и полнокопийная (не потоковая WAL-репликация), подходит для учебного объёма данных.
- Признак отказа задаётся программно (`SimulateFailure`) или реальной недоступностью контейнера.
- Восстановление считает актуальной Replica; автоматического определения «какая копия свежее» нет.
- Состояние экземпляров хранится в памяти сервера и сбрасывается при его перезапуске.
